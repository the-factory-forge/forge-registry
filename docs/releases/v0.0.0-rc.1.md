# v0.0.0-rc.1 — first source preview

Prepared on 2026-10-11 for `the-factory-forge/forge-registry`.

This is the first semantic release candidate, with no previous semantic release.
Remote inspection found no GitHub Releases and only the unrelated `v1-radix` tag;
that legacy tag is preserved. The baseline is the complete registry at
`481a8ca0fc59f21dda5edab7c6807eabc9615258`, plus the requested `package.json`
version edit, corrected reservation test selectors, aligned release guidance and
this review record. Resolve the annotated release tag to its full commit SHA after
committing. Any later publication must be a prerelease, not latest.

## Included source

The [manifest](../../registry/registry.json) defines the complete item/file and
dependency inventory. This preview distributes editable source through shadcn's
`@forge` namespace, with generated endpoints under `public/r/`.

- Public page sections and composed pages include `page-faq`, `page-contact`,
  `page-legal`, heroes, service grids, testimonials and pricing sections.
- `intranet-sidebar`, `intranet-shell`, `auth`, `employees`, `customers` and
  `projects` provide the internal workspace UI. `employees-server` supplies the
  fresh-session administrator guard; customers and projects use host callbacks.
- `drive` / `drive-storage` provide scoped folders, uploads, ZIP downloads,
  duplication and optional trash recovery. `blogs` / `blogs-storage` provide
  multilingual Markdown, publication snapshots, categories and private images.
- `menus` / `menus-storage` provide restaurant menus, translated labels, sizes,
  images, ordering and print layouts. `reservations` / `reservations-storage`
  provide appointments, overnight stays, calendars, signed management links and
  durable notification jobs.
- Shared items include `ui-shims`, `icon-tooltip`, `action-toast`, `optimistic-action`,
  `editor-form`, `dialog-submit`, table controls, semantic styling and consent
  analytics. Their dependencies install with the parent items.
- Release preparation uses `package.json`, versioned notes and the shared `release`
  skill. Repository instructions follow the
  [shared release procedure](https://github.com/the-factory-forge/forge-spec/blob/main/concepts/workflows/release-source.md):
  preparation creates a local commit and annotated tag; publication remains separate.

The showroom uses React 19, TanStack Start/Router, Tailwind 4 and Nitro. Shared UI
uses Base UI and framework shims; hosts supply routing, auth, labels, themes,
transport and business data. Exact showroom versions are in
[package.json](../../package.json) and the lockfile; item dependencies are defined
separately in the manifest.

## Integration and migration requirements

This unstable baseline does not promise compatibility with historical customer
copies or the legacy Radix tag. Review each selected item's guide and source diff.

- Supply the shared semantic colors, status pairs, layout utilities and fonts.
  The showroom stylesheet is not distributed automatically. Adapt `ui-shims` to
  the host framework and keep adapters outside registry-managed paths.
- Guard employee routes, reads and mutations with fresh-session administrator
  authorization. Supply `currentUserRole` to employee UI. Other plugin callbacks
  likewise require server-side authorization and validation.
- Drive and Blogs require explicit `<SITE_NAME>/drive/` and `<SITE_NAME>/blogs/`
  object prefixes. Old unscoped keys require a separately reviewed copy, database
  key update and verification before cleanup; installing source moves no objects.
  Menu images use Drive's scope. Review [Drive](../drive.md),
  [Blogs](../blogs.md) and [Menus](../menus.md) before adopting storage.
- Review companion SQL through the host migration workflow. Menus includes
  incremental spice-level, size and label-icon migrations; do not reapply initial
  creation SQL to existing databases or apply both shipped and generated DDL.
  See [Reservations](../reservations.md) for its schema, notification worker and
  `deriveManagementSecret` setup. Changing the management secret invalidates links.
- Blog text editing works without S3 configuration; uploads report
  `STORAGE_NOT_CONFIGURED`. Preserve custom article data when replacing old adapters.
  Project forms edit only name, status and description; host updates must preserve
  customer ownership and other fields omitted by the shared payload.

No schema or data migration is introduced by the release metadata itself. The
initial source includes the above migrations and setup requirements; none were
applied to customer systems during preparation.

  Drive's browser fixture shares port 19040 with Blogs' MinIO, so Drive was rerun

  consumer, followed by strict TypeScript validation with ES2023 libraries,
  Node/React types and host CSS declarations. No showroom aliases were used.
  Some unpinned dependencies resolved beyond showroom versions: AWS SDK 3.1149.0,

- The complete browser run finished with 156 passes and seven failures across
  163 tests. Two failures came from obsolete reservation time selectors containing

  now match the grouped timezone UI; both reservation cases passed on rerun.
  The full browser suite was not repeated after these test-only corrections.
- Five browser assertions remain unresolved: Drive's loading-to-ready table moves
  4px (`drive.browser.mjs:897`, reproduced in isolation); A4 menu preview width
  (`menu-print.browser.mjs:64`); print retry waiting for the old Saved status

  (`menus.browser.mjs:713`); and a showroom title assertion expecting "demo"
  (`showroom.browser.mjs:178`). These results prevent claiming a fully passing
  browser suite or stable-release readiness.

## Adoption and remaining limits

After publication, verify the release tag's full SHA and pin the entire `@forge`
namespace to
`https://raw.githubusercontent.com/the-factory-forge/forge-registry/<full-sha>/public/r/{name}.json`.
Install only selected items with `shadcn add @forge/<item>`, review source and
external dependency changes, then check host themes, routing, permissions,
translations, failure recovery and affected user journeys before deployment.

This preparation creates a local commit and annotated tag only. Nothing is pushed,
published or deployed, and no customer source is updated. The consumer test checks
installation and types; it does not certify each customer's adapters or visual
integration. Remote assets, live auth/email, analytics and customer migrations were
not exercised.
