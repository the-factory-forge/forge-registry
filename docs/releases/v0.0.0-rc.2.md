## Changes since RC1

- **`mailing`:** new transactional email renderer with branded HTML and matching
  plain text, validated action/logo URLs and an optional server-only Resend
  transport. The transport preserves notification IDs for idempotency and reports
  configuration or delivery failures. It adds `react-email@6.11.1` and its locked
  dependency tree. See the [Mailing guide](../mailing.md).
- **`reservations-storage`:** now declares `@forge/mailing` and renders default
  notifications as HTML and plain text. `ReservationEmail.html` is optional;
  `formatEmail` accepts synchronous or asynchronous results. Existing subject/text
  overrides remain text-only. Durable jobs, leases and retries retain their
  existing contract. See [notification integration](../reservations.md#notification-layout).
- **`auth`:** adds `AccountPage`, `AccountSecurity` and `AgentKeys` for profile
  editing, sign-in details, other-session logout and key creation/deletion. Hosts
  supply data, translations and persistence/security callbacks. The item now
  declares Base UI directly; `intranet-sidebar` and `intranet-shell` install Auth
  transitively. See [account integration](../intranet-auth.md#account-profile-and-security).
- **`drive` and `menus`:** Drive preserves breadcrumb title height between loading
  and editable states, removing the table's vertical jump. Menus corrects preview
  and print-document scrollbar styles so the host theme does not reduce paper
  width. Dependent items are `drive-storage`, `menus` and `menus-storage`.
- **`intranet-sidebar`:** its shared plugin-icon source now includes the Mailing
  icon, also reached through `intranet-shell`. The showroom adds Mailing and Account
  previews; browser assertions for menu feedback and page metadata match the UI.

This candidate includes the browser corrections documented after RC1; the
previous tag remains unchanged. Item files and direct dependencies are owned by
the [registry manifest](../../registry/registry.json).

## Integration and migrations

**No schema or data migration is introduced relative to RC1.** No database or
customer data is changed by release preparation. Existing setup requirements in
the [RC1 notes](v0.0.0-rc.1.md#before-adopting-source) still apply.

- When updating Reservations storage, install its new Mailing dependency and
  forward `email.html` alongside `email.text` to use the layout. Preserve localized
  `formatEmail` overrides, management URLs and secrets, notification IDs and retry
  policy. Default notification copy changes; hosts requiring exact wording should
  retain their own formatter.
- Mailing installation configures no email provider and sends nothing. Supply
  validated recipients, sender, credentials, trusted URLs, branding and translated
  content in server adapters. Keep password-recovery responses neutral when
  delivery fails. Never expose the server transport's credentials to browser code.
- Account UI installs no authentication backend, key storage or migration. Hosts
  enforce fresh authorization, user ownership, key expiry/encryption, session
  revocation and persistence. Pass metadata only; clear private caches on sign-out
  or account changes. Preserve existing callbacks when adding the optional UI.
- Review generated-source overwrites and host shims/styles before adoption.
  No existing registry item or public prop is removed by this candidate.

- **Registry and code passed:** regenerated endpoints match committed `public/r/`;
  `pnpm registry:check`, `pnpm typecheck` and `pnpm check` passed. The combined
  check reports zero errors and 194 existing lint warnings. Release files were

- **Unit, database and production checks passed:** all 84 unit tests, both

- **Browser checks:** the complete production suite ran 165 tests: 164 passed and

  Additional Mailing HTML/plain-text checks and rendered Mailing/Account review
  passed at 390px and 1280px, including dark Account screens, without page overflow
  or browser errors.
- **Consumer install passed with the workaround below:** shadcn `4.21.1` installed
  Auth, Mailing, Reservations storage, Menus storage, Drive storage and the intranet
  sidebar, including their dependencies, into a disposable consumer. Strict
  TypeScript passed with ES2023, explicit Node/React types and host CSS declarations.
  The consumer has no showroom aliases. Unpinned packages resolved to AWS SDK

- **Not rerun:** Drive, Blogs and Menus storage suites; their server implementations
  are unchanged since RC1. Live providers, customer authentication and customer

**Known installation limitation:** one shadcn command containing Auth, Mailing,
Reservations storage, Menus storage, Drive storage and the intranet sidebar
rewrote Reservations' `renderEmail` import to `@/components/plugins/auth` and failed
TypeScript. Running `shadcn add @forge/reservations-storage --yes --overwrite`
separately restored the correct Mailing import and the full consumer typecheck
passed. Install Reservations storage separately after other selected items;
inspect that import and run host type checks before adopting this RC. The release
does not change registry source to work around the CLI transformation.

The fresh pnpm consumer also required `allowBuilds.esbuild` to be `true` in
`pnpm-workspace.yaml`, as in this repository, before dependency installation
completed. Initial worktree checks hit a
package-runner/dependency setup issue; the passed checks above used an isolated
dependency directory and the pinned pnpm `12.8.1` runtime.

## Adoption and limitations

After publication, verify the selected tag's full SHA and pin the entire `@forge`
namespace to that revision:

```text
https://raw.githubusercontent.com/the-factory-forge/forge-registry/<full-sha>/public/r/{name}.json
```

1. Install only selected items with the pinned shadcn CLI. Install
   `reservations-storage` separately, after any combined install.
2. Review dependencies and source changes, including the Mailing import.
3. Check host types, routes, permissions, translations, themes, email
   content/delivery and failure recovery before deployment.

An immutable source URL does not pin unversioned npm dependencies or prove which
source a customer has installed.

Browser email previews do not certify every inbox client. Live provider delivery,
real authentication, customer adapters and deployments are separate checks.
Existing customer adoption records are not revalidated by this preparation.

This local preparation follows the [shared release procedure](https://github.com/the-factory-forge/forge-spec/blob/main/concepts/workflows/release-source.md).
It does not push, create a GitHub Release, deploy or update customer source.
