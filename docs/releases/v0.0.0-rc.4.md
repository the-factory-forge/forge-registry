## Changes since RC3

- **`employees` and `employees-server`:** creation accepts name, email and role
  without a password. The service awaits invitation delivery and returns its
  outcome. Failed delivery preserves the created account and offers a resend
  path instead of duplicate creation. Pending accounts receive invitations;
  activated accounts retain verification mail. Disabled accounts cannot be invited.
- **`customers`:** creation removes temporary passwords, generation/copy controls,
  password limits and their labels. Hosts own account invitations; contacts
  without an email remain supported.
- **`blogs` and `blogs-storage`:** public article cards have one link covering the
  whole card, keyboard focus and reduced-motion support. Image uploads use
  ordinary S3 PUT requests for providers that reject conditional PUTs. Fresh UUID
  keys keep same-name images separate and existing asset references stable.
- **`drive` and `auth`:** embedded Drive roots omit a redundant breadcrumb row
  unless back navigation or space renaming needs it; folder breadcrumbs remain.
  Password-form feedback appears below the submit button, with space reserved.
- **Showroom:** account previews use the intranet layout, including mobile
  navigation and host-provided content. Active preview controls use bolder text.

No item, npm dependency or lockfile change is introduced. Registry dependencies
also reach `intranet-sidebar`, `intranet-shell`, `projects`, `drive-storage`,
`menus` and `menus-storage`; review selected installs and their transitive updates.
The [manifest](../../registry/registry.json) owns the exact dependency graph.

## Breaking integration and migrations

**Schema and data migrations: none relative to RC3.** Existing credentials,
objects and asset IDs are not rewritten. The callback and type changes below
require host code updates.

1. Change employee `onCreate` to return `{ invitationSent: boolean }` after
   persistence and cache refresh. Remove password inputs and old password label
   overrides; translate invitation, resend, failure and close labels. Supply
   `mustChangePassword` so pending accounts expose the invitation action.
2. Supply `sendInvitation(employee, invitationURL)` to `createEmployeeService`.
   Pass the invitation URL to `create(input, invitationURL)` and
   `sendVerification(input, callbackURL, invitationURL)`. Construct URLs from the
   configured origin and validated locale. Creation requires configured email;
   await actual delivery and retain the created account on delivery failure.
3. Implement the host invitation lifecycle in the [Auth guide](../intranet-auth.md):
   random, single-use tokens expiring after one hour; resend and administrator
   edits revoke outstanding links. Acceptance sets the chosen password, verifies
   email ownership, clears pending onboarding and revokes old sessions while
   preserving role. Derive the recipient from the valid token. Keep fresh-session
   admin authorization and existing temporary-password account guards. The registry
   does not supply token issuance, real email delivery or an acceptance endpoint.
4. Remove `password`, `passwordMinLength`, `passwordMaxLength`, password labels
   and `generateCustomerPassword` usage from customer adapters. Do not expect a
   password in `CustomerCreateValues`. Hosts that grant access must issue their
   own invitations. See the [Customers guide](../customers.md).
5. Keep account routes accessible inside the intranet shell for signed-in roles,
   with management navigation filtered and onboarding/server guards intact.
   Blogs storage keeps its site/plugin prefix and private bucket requirements;
   migration scripts must still reject destination objects with different bytes.
