## Changes since RC2

- **`auth` passwords:** reset and change forms ask for the new password once,
  without confirmation. Signed-in changes require the current password and send
  `{ currentPassword, newPassword }`, preserving the RC2 callback contract.
  Independent Show/Hide controls preserve values, support keyboard tooltips and
  disable while pending. Successful changes clear and hide both fields; failed
  submissions preserve drafts and reserve error space. Reset recovery links sit
  beside the password hint.
- **`auth` login:** optional `defaultEmail` and `verificationStatus` support the
  return from verification emails. Success shows one dismissible toast; errors
  show recovery guidance. Hosts still validate tokens and own account state.
- **`auth` accounts and keys:** `AccountPage` accepts host `header` and `content`
  for existing routed profiles. `AgentKeys.onCreate` is optional, and key metadata
  supports a revoked state that takes precedence over expiry.
- **`customers` and `employees`:** temporary-password fields gain accessible
  Show/Hide controls that retain their value and return to hidden after success.
  Dependencies also reach `projects` and `employees-server`.
- **Showroom:** localized `/login` is the authentication example and canonical
  URL; the old `/auth` and `/change-password` routes are removed. Account Security
  demonstrates authenticated changes. `ChangePasswordPage` remains exported for
  existing host compatibility. `intranet-sidebar` and `intranet-shell` receive
  Auth transitively.

No registry item or dependency is added. Package dependencies and the lockfile are
unchanged. The [registry manifest](../../registry/registry.json) owns item files
and dependencies.

## Integration and migrations

**No schema or data migration is introduced relative to RC2.** No customer source,
database, authentication service or deployment is changed by this release.

1. Keep server-side validation of the current password and a fresh session for
   signed-in changes. Hosts that adopted the intervening new-password-only source
   must restore that check. Derive the target account from the session, enforce
   password policy and preserve CSRF protection, revocation and onboarding rules.
   Recovery still requires a valid, unexpired, single-use server token.
2. Keep `currentPassword` label overrides. Remove obsolete `confirmPassword` and
   `passwordsMismatch` overrides; add translated Show/Hide and verification copy
   as needed. The new-password policy does not constrain the current password.
3. Configure verification-email callbacks and validated login search parameters
   as described in the [Auth guide](../intranet-auth.md#returning-from-email-verification).
   Provider errors take precedence over success hints. Search values control UI
   only and never grant access; previously sent emails keep their old callbacks.
4. Preserve host profile routes, forms, permissions and persistence when using
   account composition or optional key creation. Removing a showroom route does
   not change customer onboarding routes. See the [Auth guide](../intranet-auth.md).

The callback matches RC2; removal of confirmation-related label keys can still
require TypeScript updates in hosts that supplied them.
